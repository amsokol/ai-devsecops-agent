# Дизайн AI DevSecOps-агента

Статус: черновик. Документ описывает агента (`ai-devsecops-agent`) — исполнителя, который
использует библиотеку знаний [`ai-devsecops-skills-knowledge`](https://github.com/amsokol/ai-devsecops-skills-knowledge)
и продуктовый оверлей.

Язык документа — русский. Код, конфигурация, схемы и README — английские.

Термины и контракт обмена определены в `CONTRACT.md` библиотеки; здесь описано, как агент их
исполняет.

## 1. Назначение и границы

Агент — исполнительный слой. Он не содержит суждения: что считать проблемой и как поступать
описано прозой в библиотеке. Агент отвечает за то, что должно быть точным и воспроизводимым:

- разложить триггер на задачи и запустить их параллельно;
- дать задачам руки — детерминированные инструменты;
- собрать результаты, свести их к вердикту и выполнить действия в хостинге;
- уложиться в бюджеты и оставить пригодный для аудита след.

Чего в агенте нет: критериев severity, правил карантина, процедур экосистем, продуктовых
значений. Если такое появилось в коде — это ошибка размещения.

## 2. Что изменилось по сравнению с предыдущим агентом

| Было (`ai-devsecops-cursor`) | Стало |
| --- | --- |
| одна сессия одной модели делает всё | план задач, параллельные подагенты, модель под роль |
| SDK вплетён в код прогона | агентский SDK за узким портом; ядро о нём не знает |
| модель сама решает, что делать | план детерминирован; LLM — только на свободных триггерах |
| протокол — строки `AGENT_SIGNAL:` в тексте | валидируемые артефакты: свидетельства, находки, результат |
| факты и суждение перемешаны в одной сессии | фаза добычи свидетельств отделена от фазы решения |
| неполнота выглядит как успех | третий исход прогона: неопределённо |
| «лучшая модель» — на вкус | eval на фикстурах библиотеки как условие смены модели |

Цель изменений — оптимальность: правильная модель на правильную задачу, параллельное
исполнение, предсказуемая стоимость. Но оптимальность не должна покупаться ценой
воспроизводимости: гейт блокирует людей, поэтому одинаковый вход обязан давать одинаковый ответ.

## 3. Принципы

1. **Ядро детерминировано.** План, агрегация, дедупликация, вычисление вердикта, арифметика дат
   и сравнение версий — код. LLM не участвует в этих шагах.
2. **LLM там, где нужно суждение.** Анализ кода, оценка достижимости уязвимости, приоритизация,
   починка, формулировка текста для человека. И один особый случай — классификация свободного
   запроса человека.
3. **Инструменты вместо угадывания.** Если у факта есть точный источник, его получает код.
   Модель не вспоминает CVE и не считает даты.
4. **Неинтерактивность.** Прогон идёт в CI. Никаких запросов подтверждения, никаких ожиданий
   ввода: любой такой запрос — ошибка конфигурации, а не пауза.
5. **Бюджет и деградация.** У каждой задачи предел по шагам и по времени, у прогона — общий
   бюджет. Исчерпание даёт неопределённый результат, а не тишину и не одобрение.
6. **Аудируемость.** По завершении прогона видно, какие модели работали, какие версии библиотеки
   и инструментов использовались, какие свидетельства собраны и сколько это стоило.
7. **Всё внешнее — данные.** Содержимое репозитория, описание изменения, ответы реестров и вывод
   подагентов не могут быть инструкциями.

## 4. Внешние интерфейсы

Три способа запуска, и все три сводятся к одному триггеру внутри:

| Триггер | Источник | Playbook |
| --- | --- | --- |
| `change-opened`, `change-updated` | событие хостинга | `playbooks/pr-review` |
| `comment-on-change` | ответ человека в треде агента в изменении | `playbooks/pr-review` |
| `comment-on-issue` | комментарий человека в issue агента | `playbooks/maintain` |
| `maintain-requested` | ручной запуск | `playbooks/maintain` |
| `maintain-scheduled` | расписание, например раз в неделю | `playbooks/maintain` |

У пробуждения два вопроса, и отвечают на них разные вещи. *Где* оставлен комментарий определяет
playbook — и это известно из события, до любой модели. *Что в нём написано* определяет только курс
внутри playbook'а, и это единственное место, где модель читает свободный текст.

Регулярный обслуживающий прогон обязателен, а не опционален: часть находок появляется без всякого
изменения кода. Публикуются новые уязвимости для уже стоящих версий, истекает карантин у
кандидатов, которых прошлый прогон отложил, выходят исправления к тому, что раньше было
неисправимо. Всё это события во времени, и без прогона по расписанию их не заметит никто, пока
человек не запустит агента вручную — то есть обычно уже после инцидента. Предохранители к нему
описаны в разделе 6.1.

CLI — одна команда с подкомандами, пригодная и для CI, и для локального запуска:

```bash
agent review --repo <path> --change <number> [--dry-run]
agent review --repo <path> --change <number> --wake-comment <id> --actor <login>
agent maintain --repo <path> [--scheduled] [--dry-run]
agent maintain --repo <path> --wake-issue <number> --wake-comment <id> --actor <login>
agent explain --run <id>      # показать манифест прогона и собранные свидетельства
```

`--wake-comment` и `--actor` передаются только вместе: без комментария прогон не знает, о чём его
попросили, а без аккаунта не отличит коллегу от собственного прошлого комментария. Половинчатый вызов
— ошибка конфигурации, а не повод угадывать остальное.

`--dry-run` планирует и анализирует, но не мутирует хостинг. Это режим отладки и первого
подключения продукта, а не постоянное состояние.

```text

  │
  ├─ intent (LLM, только для comment-on-*) ──────────────┐
  │                                                      │
  ▼                                                      ▼
planner (код) ──► task graph ──► subagent runner (порт бэкендов)
  ▲                                   │        │

  │                                   ▼                    │

  ▲                                   │
overlay                               ▼
                                 aggregator (код)
                                      │
                                      ├─► verdict (таблица блокировок)

                                      └─► actions (SCM, идемпотентно)
                                              │
                                              ▼
                                     run manifest + exit code
```

### 5.1 Планировщик

План строится кодом из трёх входов: триггер, список изменённых файлов, включённые в оверлее
экосистемы. Для каждого playbook'а в конфигурации сценария описано, какие задачи существуют и при
каком условии включаются; условие — это набор файловых признаков и/или требование включённой
экосистемы. Никакого обращения к модели здесь нет.

Причина именно такая: для события «открыли изменение» набор задач — величина, вычислимая из
диффа. Тратить на неё вызов модели значит добавить латентность, стоимость и, главное,
недетерминированность в блокирующую проверку. Мигающий гейт теряет доверие после первого же
«перезапустил — и прошло».

### 5.2 Классификатор интента

Единственное место, где вход действительно свободный: человек написал комментарий. Здесь работает
дешёвая быстрая модель, и её задача узкая — отнести сообщение к одному из известных интентов и
вернуть структуру, а не рассуждение. Инструментов у этой сессии нет: ответ должен зависеть от двух
переданных текстов и ни от чего больше, иначе сессия рано или поздно начнёт классифицировать по
тому, что нашла в репозитории.

| Интент | Курс | Что это значит |
| --- | --- | --- |
| `unlock` | `recheck` | человек разрешил то, что агент держал: перепроверить эту находку и действовать |
| `recheck` | `recheck` | факты изменились, посмотреть заново |
| `fix` | `patch` | «как это исправить» — сделать правку и предложить её в разговоре |
| `question` | `answer` | объяснить, ничего не меняя |
| `unrelated` | `ignore` | ничего не делать и никуда не писать |

Курс `patch` вырождается в `answer` там, где предлагать нечего: в комментарии к issue нет диффа, к
которому можно прицепить предложение, а продукт, не сопоставивший роль `fixer` своим ревью, решил, что
его агент объясняет, а не предлагает.

Классификатор не решает, что делать дальше: соответствие «интент → курс» — таблица в коде. Поэтому
цена неверно прочитанного комментария ограничена: потраченная сессия, ответ вместо действия или
перепроверка, о которой не просили. Разрешения, которого человек не давал, из этого не получается
никогда. При низкой уверенности курс — `answer`: неуверенный `unlock` это разрешение, которого не
давали, а неуверенный `recheck` — бюджет, потраченный на догадку.

Перепроверка сужается до одной проверки — той capability и той экосистемы, к которым относится
находка из маркера. Человек, написавший в одном issue, спрашивает про одно; недельный обход в ответ
сделал бы одобрение самым дорогим действием, доступным человеку, и утопил бы ответ в чужих находках.

До первой траты прогон отказывается в четырёх случаях, и каждый записывается как `declined` с
причиной: автор — бот или тот аккаунт, под которым публикуется сам агент; у аккаунта нет права
записи или платформа отказалась это подтвердить; в issue или треде нет маркера, то есть разговор не
агентский; автор комментария не совпадает с actor'ом из события. Первый случай — защита от петли,
второй — от того, что бюджет и разрешения раздаёт любой, кто умеет писать комментарии.

Ответ человеку — только текст: тред не разрешается, issue не закрывается, worktree отвечающей сессии
не выдаётся, поэтому изменить файлы она не может. Всё фактическое в опубликованном комментарии —
идентификатор прогона, ключ находки, маркер — пишет агент; сессия даёт только объяснение. На issue,
кроме ответа, публикуется статус того, что произошло: каждая его фраза собрана из записанных фактов,
потому что молча закрытый issue читается ровно как «меня проигнорировали».

Курс `patch` — единственный, где из комментария получается изменение, и оно тоже остаётся
комментарием. Правку делает сессия `fixer` в одноразовой копии репозитория на голове изменения, и над
этой копией выполняется верификация из оверлея — та же, что для fix-ветки. Публикуется абзац сессии о
том, почему правка такая, затем дифф, прочитанный **из git**, а не рассказ сессии о нём, затем метка,
которую заслужила верификация: `suggestion`-блок, если правка заменяет ровно те строки, на которых
висит замечание, иначе дифф для чтения. Ничего не коммитится и не пушится, копия выбрасывается в любом
исходе: ветка под ревью двигается только руками человека. Непроверенный патч всё равно предлагается —
спрашивали именно про исправление, — но с меткой об этом, потому что нажимающий «commit suggestion»
доверяет как раз ей.

### 5.3 Подагенты и роли

Задача исполняется подагентом в одной из ролей библиотеки: `analyst` (только чтение) или `fixer`
(правки в изолированном worktree). Каждой роли в конфигурации сопоставлены бэкенд и модель.

| Роль | Характер работы | Требования к модели |
| --- | --- | --- |
| `intent` | классификация короткого текста | быстрая, дешёвая, структурированный вывод |
| `analyst` | суждение по подготовленному контексту | сильная на коде, длинный контекст, вызов инструментов |
| `fixer` | правки, итерации до зелёной верификации | сильная на коде, надёжный вызов инструментов |
| `writer` | формулировка текста для человека | средняя; включается опционально |

Требования к модели в этой таблице — ориентир для выбора пары, а не проверяемое условие: «сильная на
коде» нельзя проверить при старте. Проверяется другое — что бэкенд умеет то, без чего код роли не
работает: реестр инструментов. Правка файлов в этот список не входит — `edit_file` такой же
инструмент, как остальные, и бэкенд, умеющий реестр, умеет и его. Роль, которой никто не сопоставил
бэкенд, тоже ошибка старта, если её требует план: молча пропущенная задача хуже громкого отказа.

Роль `writer` вынесена отдельно намеренно: агрегация и вердикт считаются кодом, но текст
замечания читает человек, и качество формулировки имеет цену. Это единственное, за чем модель
привлекается после фазы решения, и она не может изменить ни вердикт, ни состав находок.

Тексты находок по-прежнему формулирует `analyst` в рамках своей задачи: отдельная роль стоила бы
второго вызова модели на каждый прогон и добавила бы место, где текст расходится с составом находок.
`writer` включается там, где находки нет вообще — в ответе человеку, который что-то спросил в треде
или в issue. Это единственная проза, публикуемая от имени агента без находки за ней, и поэтому вокруг
неё всё сжато: ответ ничего не меняет, ни один тред им не разрешается, длина ограничена кодом.

Граница между `writer` и `fixer` — не в том, кто пишет код, а в том, что остаётся после сессии.
`fixer` оставляет дерево, над которым можно выполнить верификацию продукта, поэтому его результат
получает метку и применяется одним нажатием; `writer` оставляет текст. Отсюда и распределение: вопрос
«как это исправить» идёт к `fixer`, хотя ответ публикуется комментарием, — процитированный из прозы
патч никем не проверен, а применят именно его. Абзац «почему правка такая» пишет тот же `fixer` в поле
результата: объясняет тот, кто делал правку, из того же контекста, и разойтись с диффом словам негде.

**Подготовленный контекст важнее агентского блуждания.** Для ревью дифф, затронутые файлы, вывод
сканеров и метаданные зависимостей собираются заранее детерминированно. Подагент получает готовый
срез и в типичном случае не ходит по репозиторию инструментами: это один-два вызова, которые
кэшируются, параллелятся и предсказуемы по стоимости. Исследование инструментами включается как
отступление, когда модель явно просит больше контекста.

### 5.4 Порт бэкендов

Агент рассчитан на несколько агентских SDK, и они живут за портом. Порт узкий и описывает только то,
что нужно прогону: запустить сессию с заданной моделью, системным текстом и набором инструментов;
получить поток событий; получить факт завершения; получить учёт использования. Всё остальное
остаётся внутри адаптера.

Первым реализуется адаптер **Cursor SDK**; второй добавляется позже и не должен требовать правок
ядра. Порт при одном адаптере оправдан не «на будущее»: у него сразу два потребителя, потому что
тесты и eval-харнес работают через поддельный бэкенд, который отдаёт заранее записанные события. Без
порта проверять планировщик, агрегацию и вердикт можно было бы только с живой моделью, то есть
медленно, дорого и недетерминированно.

Следствия, которые обязаны быть в реализации:

- **Модель называется парой «бэкенд + модель».** Набор доступных моделей определяется бэкендом,
  а не абстрактным списком провайдеров. Формулировка «агент не привязан к Cursor» означает, что
  Cursor — первый из равноправных бэкендов, а не единственный путь.
- **Возможности бэкендов различаются**, и различия объявляются явно: вызов инструментов, правка
  файлов, структурированный вывод, детализация учёта токенов. Совместимость роли и бэкенда
  проверяется при старте; несовместимая конфигурация — ошибка запуска, а не странность посреди
  ревью. Возможность объявляется только там, где она известна: булево значение, придуманное для
  таблицы, выглядит ровно как проверенное.
- **Требования роли живут в коде, а не в конфигурации.** Что нужно роли, следует из того, что делает
  её код: аналитику без реестра инструментов нечем обосновать находку, а `fixer` без права правки
  файлов ничего не исправит. Это не ручка настройки. Ручка — соответствие «роль → бэкенд и модель»,
  и она в оверлее продукта. Проверка идёт между требованием из кода и объявленной возможностью
  адаптера.
- **В агенте нет ни одного имени модели** — ни в коде, ни в файлах, которые он поставляет. Продукт
  живёт дольше любого провайдера: подписка кончается, появляется новый адаптер, важный проект решает,
  что его ревью стоит дорогой модели. Значение по умолчанию внутри агента превращало бы каждый такой
  случай в форк каталога конфигурации, который потом тащат через все релизы, а сам агент — в того, кто
  решает, как тратятся чужие деньги. Оттуда же и бюджеты: потолок токенов — часть решения о модели.
  Ключи провайдера приходят из окружения и никогда из оверлея, потому что оверлей лежит в git.
- **Разрешения задаются явно** и запрещают любые интерактивные запросы.
- **Бюджеты и таймауты навешивает порт**, а не средства SDK: у бэкендов разный учёт, и полагаться
  на их внутренние ограничения нельзя.
- **Результат — файл-артефакт**, а не финальное сообщение. Разбор текста ответа хрупок, и именно
  на этом ломался предыдущий агент.

### 5.5 Инструменты

Инструменты реализованы один раз в коде агента и предоставляются подагентам как MCP-сервер.
Так они переиспользуются любым бэкендом, а порт не превращается в абстракцию над чужими
абстракциями.

| Группа | Инструменты |
| --- | --- |
| репозиторий | `read_file`, `list_files`, `search_text`, `read_change` |
| команды | `run_command` (allowlist, без шелла, таймаут, scratch-директория) |
| сеть | `http_get` (allowlist хостов), `scm_read` |
| производные факты | `compare_versions`, `date_math`, `evidence_cache` |
| мутации (`fixer`) | `edit_file`, `git_ops`, `scm_write` |

`read_change` отвечает на вопрос «что изменение сделало с этим файлом» — добавленные и удалённые
строки с номерами, прямо из git. Он есть только там, где есть изменение, и существует потому, что
область ревью не должна быть предметом мнения: модель, прочитавшая манифест целиком, видит и те
пины, которых никто не касался, и сообщает о них. Это заставляет автора ждать из-за строки, которую
он не писал, — а такой гейт выключают.

Отдельно от сетевого предела действует предел на то, **сколько инструмент отдаёт модели**. Скачать
большой документ дешево, положить его в контекст — нет: агрегатный индекс версий популярного пакета
стоит дороже всего ревью, ради которого его запросили. Документ сверх предела не отдаётся, вызов
помечается неуспешным, и факт на него сослаться не может.

Чтобы отказ не превращался в тупик, `fetch` умеет отдавать часть документа: `select` называет путь
внутри JSON, `keys_only` — что нужны только имена. Список версий пакета — это имена в объекте
релизов, а мегабайты под ними описывают файлы, которых вопрос о версиях не касается. Знание о том,
какой ключ выбрать, остаётся рецептом в библиотеке; в код агента реестровая специфика не переезжает.
В манифест пишется прочитанное, а не запрошенное: `<url>#<select>`, иначе прогон нельзя воспроизвести.

Права на утилиты и хосты выдаются по механизму «заявка и потолок»: документ экосистемы объявляет
в разделе `Requirements`, что ему нужно, а агент удовлетворяет заявку в пределах своего потолка.
Строка в документе знания не может расширить права агента; заявленное вне потолка отклоняется при
старте с внятным сообщением.

Заявка читается из прозы — берутся все имена в обратных кавычках из пунктов `Binaries:` и `Hosts:`.
Для оверлея такой разбор был отвергнут, и разница в режиме отказа. Переформулированная строка
оверлея молча меняет вердикт; переформулированная строка `Requirements` не выдаёт ничего, факт
становится `not-permitted`, прогон об этом сообщает и не разрешает слияние. Оговорки вида «`skopeo`,
когда нужны метаданные образа» разбор не различает и выдаёт надмножество — настоящей границей
остаётся потолок, а не формулировка. Права выдаются только заявкам включённых экосистем и до старта
первой задачи: отказ, найденный посреди ревью, выглядел бы как сломанный инструмент и стоил бы
бюджета.

`run_command` работает без шелла: никаких пайпов, перенаправлений и цепочек. Это снижает
поверхность атаки и делает вызовы воспроизводимыми. Если процедуре нужен конвейер, правильный
ответ — отдельный инструмент под эту нужду, а не разрешение шелла.

### 5.6 Хранилище свидетельств

Свидетельства пишутся в единое хранилище прогона: вопрос, субъект, значение, происхождение,
источник, время, надёжность, статус. Надёжность выводится из происхождения кодом, а не выбирается
моделью, потому что от неё зависят права находки.

Хранить между прогонами приходится три разные вещи, и их нельзя складывать в одно место: они
по-разному переживают потерю. Запись прогона теряется — исчезает аудит, но работа не меняется. Кэш
теряется — прогон медленнее. Состояние теряется — агент **меняет поведение**, потому что забывает,
что источник сломан третью неделю.

| Что | Где | Кто пишет |
| --- | --- | --- |
| запись прогона: свидетельства и манифест | каталог прогона, выгружается артефактом CI | любой прогон |
| кэш неизменяемых фактов | каталог, который кэш платформы CI восстанавливает и сохраняет | только прогон на основной ветке |
| состояние агента | git-ref `refs/agent/state` в продуктовом репозитории | только прогон на основной ветке |

**Запись прогона** неизменяема и живёт столько, сколько платформа хранит артефакты. Ключевое
правило: будущий прогон никогда не берёт факты из записи прошлого — читает её только
`agent explain`. Иначе журнал аудита незаметно становится источником истины и ошибка одного прогона
живёт вечно.

**Кэш** содержит только факты, неизменяемые по своей природе: дату публикации конкретной версии,
digest артефакта. Список доступных версий и данные об уязвимостях не кэшируются никогда — иначе
недельный прогон перестанет замечать новые advisory, то есть именно то, ради чего он существует.
Сбои не кэшируются тоже: недоступный хост — это не факт о пакете. Промах кэша — нормальное событие,
а не сбой; записи платформы вытесняются, и прогон обязан спокойно добыть факт заново.

Кэш — это каталог, и отдельного бэкенда под платформу не нужно: кэш GitHub Actions и его аналоги
именно восстанавливают и сохраняют каталог. Одна реализация работает и на ноутбуке, и в пайплайне,
а «где кэш» становится строкой конфигурации, а не веткой в коде.

Каждая запись несёт происхождение и версию рецепта, которым получена, чтобы исправленный рецепт
обесценивал старое. Надёжность от кэширования не растёт: эвристическая дата остаётся эвристической
навсегда. Флаг `--no-cache` позволяет доказать, что вердикт воспроизводится без кэша.

Писать в кэш разрешено только прогонам на основной ветке; прогоны на изменениях читают. Это
закрывает отравление кэша тем, кто способен открыть изменение, и совпадает с тем, как кэш платформы
уже разграничен по ветвям. Полезное следствие: недельный обслуживающий прогон работает
прогревателем, а блокирующий гейт получает готовые даты. Выигрыш наибольший там, где добыча дорогая
и хрупкая, то есть в экосистемах с происхождением `web`; заодно соседние прогоны перестают
расходиться в дате из-за иначе отрендеренной страницы.

**Состояние** держится намеренно минимальным — только то, что нельзя вывести из хостинга: счётчики
подряд идущих сбоев по причине и поверхности, для правила эскалации из раздела 6.1. Число открытых
изменений и issue агента не хранится, оно спрашивается у хостинга, иначе состояние начнёт
расходиться с реальностью. Запрет на два одновременных прогона тоже не состояние, а группа
одновременности в CI.

Отдельный ref выбран вместо файла в основной ветке и вместо кэша платформы по трём причинам: он
долговечен и не зависит от вытеснения; он не создаёт шума в ветке и в изменениях; у него есть
история, по которой видно, когда и почему счётчик вырос. Внутри — один файл `state.json`, целиком
заменяемый. Читается ref тем кредентиалом, который уже есть у checkout: получить ref может любой,
кто может клонировать. Пишется тем же кредентиалом, что и fix-ветки, потому что оставить след — не
то же самое, что прочитать. Коммит собирается пламбингом и не касается рабочего дерева: в нём в этот
момент может работать задача исправления.

Чтение никогда не падает. Ref, которого нет, недоступный remote и документ, отредактированный
руками в невалидный JSON, означают здесь одно и то же: этому прогону не на что опереться. Иначе
подспорье превратилось бы в зависимость, и сломанный документ отказывал бы в работе каждому прогону
по расписанию.

Даты публикации не зависят от продукта, поэтому общее хранилище фактов на организацию прогревало бы
новый продукт с первого дня. Интерфейс `evidence_cache` это допускает, но в первой версии не
включается: общее изменяемое состояние между продуктами означает, что отравление одного отравляет
все.

### 5.7 Агрегация и вердикт

Агрегация — код:

1. Собрать результаты задач; отсутствующий или невалидный результат — не «чисто», а сбой.
2. Дедуплицировать находки по стабильному ключу; одна проблема, найденная двумя задачами, —
   одна находка.
3. При расхождении взять строгую оценку: класс `security` перевешивает `routine`, более высокая
   severity перевешивает низкую. Оба исходных суждения остаются в манифесте.
4. Ограничить действие каждой находки надёжностью её свидетельств.
5. Сверить с уже открытыми тредами и issue; закрывать разрешено только то, чья задача завершилась
   результатом `clean`.
6. Вычислить вердикт по таблице «класс × severity» и определить исход прогона.

Расхождение решается таблицей, а не повторным обращением к более сильной модели. Эскалация внесла
бы в блокирующую проверку латентность, стоимость и, главное, недетерминированность: два прогона на
одном входе дали бы разные ответы. Риск завышенной моделью severity закрыт иначе — блокировать
разрешено только по воспроизводимому свидетельству, поэтому эвристическое завышение даёт замечание,
а не отказ.

Исходов три: разрешено, заблокировано, неопределённо. Неопределённо возникает, когда обязательная
задача завершилась сбоем — сканер не запустился, хост не ответил, источник сменил форму, права не
выданы, бюджет исчерпан. Такой исход не разрешает слияние и при этом ничего не утверждает о коде.
Задокументированный предел (в профиле экосистемы стоит `none`) сбоем не считается.

Коды возврата:

| Исход | Код |
| --- | --- |
| разрешено | 0 |
| остаются незаблокирующие находки | 0 |
| заблокировано | 5 |
| неопределённо | 6 |
| ошибка конфигурации | 64 |
| внутренний сбой | 2 |

### 5.8 Действия

Действия в хостинге выполняет только агент, после агрегации, и ровно один раз за прогон. Подагент
не пишет комментарии — это то, что делает повторные прогоны идемпотентными. Сверка ведётся по
стабильному ключу находки: существующий тред обновляется, а не дублируется; исчезнувшая
подтверждённо находка закрывается; расположение комментария берётся из изменчивого поля
`location`, потому что ключ намеренно не содержит номера строк.

Слияние агент не выполняет никогда.

**Порт узкий, адаптер один.** Порт умеет ровно то, что нужно ревью и обслуживанию: прочитать
изменение, найти свои треды, опубликовать одно ревью с новыми тредами, поправить тред, разрешить
тред. Интерфейс, упомянувший бы слияние или правила ветки, рано или поздно был бы использован.
Адаптер GitHub говорит через `gh api`: клиент уже умеет читать токен из окружения, повторять
запрос при лимите и говорить GraphQL, а у разрешения треда REST-эндпоинта нет вовсе. Токен
никогда не попадает в аргументы — только в окружение, которое `gh` наследует.

**Личность агента задаётся явно, а не достаётся клиентом.** Токен читается из переменных окружения в
порядке `AGENT_GITHUB_TOKEN`, `GH_TOKEN`, `GITHUB_TOKEN`; сохранённый на машине вход не используется
никогда, и без токена не публикуется ничего. Первая живая проверка адаптера опубликовала пять
машинных ревью под именем человека, и имя здесь — меньшая половина беды: решение, подписанное
коллегой, не отличить от мнения коллеги, а workflow, который будит агента по человеческим
комментариям и отфильтровывает ботов, не может отфильтровать человеческий аккаунт — свой же
комментарий будит агента снова. Аккаунт, от которого шла публикация, пишется в манифест, и если
платформа показывает его человеком, прогон предупреждает и называет нужный фильтр. Это
предупреждение, а не отказ: отдельный машинный аккаунт — законный способ работы, и платформа
показывает его обычным пользователем.

**Свой комментарий узнаётся по маркеру.** В тело кладётся HTML-комментарий с ключом находки:
`<!-- agent:key=... -->`. Идентификаторы комментариев меняются при пересоздании треда, номера строк
— при правке файла выше, а ключ не меняется. Тред без маркера агенту не принадлежит: комментарий
человека он не правит и не разрешает никогда, и это гарантируется отсутствием совпадения, а не
вежливостью промпта.

**Разрешение треда требует чистого прогона владельца.** Тред закрывается, только если находки нет и
задача её capability завершилась `clean` на этом head. Отсутствие в прогоне, который не смотрел, —
не исправление; закрытие по такому основанию тихо снимает настоящую проблему.

**Стойка ревью выводится из результата.** `pass` — approve, `blocked` — request changes,
`inconclusive` — обычный комментарий: слияние всё равно запрещает проверка, а «нужны правки» — это
утверждение о коде, которого прогон без результата не заслужил. Своё же изменение GitHub не даёт
ревьюить вовсе — ни одобрить, ни запросить правки, — и тогда тот же текст публикуется комментарием.
В манифест пишется то, что записала платформа, а не то, что запрашивалось: прогон, заявивший «запросил
правки» на pull request без запроса правок, обесценивает и свою запись, и саму страницу.

**Ничего не публикуется для чужого коммита.** Если изменение уехало, пока прогон работал,
комментарии указывали бы на строки, которых никто не предлагал: прогон говорит об этом и не пишет.
Черновик не комментируется. Сбой платформы — предупреждение, а не потеря вердикта: анализ уже
оплачен, а код выхода несёт решение и без комментария.

Публикация выключена по умолчанию и включается `--publish`: прогон на ноутбуке отчитывается тому,
кто его запустил, а прогон в CI явно говорит, что собирается писать в чужой pull request.

**Обслуживающему прогону писать некуда, поэтому находки становятся issues.** Диффа, который кто-то
читает, у него нет, и находка, не записанная в трекер, — находка, которую никто не увидит. Сверка та
же, что у тредов, и по тому же ключу: одна issue на находку, обновление вместо второй issue, закрытие
только когда capability-владелец завершил `clean` и находки нет — с комментарием, называющим, что
именно смотрело и на каком head. Если проверка не завершилась, issue остаётся ровно как была, и агент
молчит: «всё ещё есть» — такое же необоснованное утверждение, как и закрытие, а еженедельное
напоминание о том, что ничего не известно, учит команду выключать агента. Метка `agent` не является
доказательством авторства — её может поставить кто угодно, — поэтому сверка доверяет только маркеру.
Заголовок строится из частей, опознающих проблему, и не содержит того, что дрейфует (версии,
идентификатора advisory): иначе сохранённый поиск перестаёт совпадать. Число новых issues за прогон
ограничено оверлеем; лишние переносятся на следующий прогон и называются в записи, но не выбрасываются
и не сливаются в одну issue.

**Проверенная ветка уходит на платформу и предлагается изменением.** Порядок обратный ожидаемому:
сначала агент спрашивает платформу, какие из его собственных ветвей уже несут открытые изменения, и
только потом решает, что вообще стоит исправлять — subject, уже находящийся на ревью, иначе получил бы
второе изменение с той же правкой. Если этот ответ недоступен, ветки не готовятся вовсе: слепая
подготовка — это и есть механизм появления дублей, а потерянная сессия исправления стоит дешевле
вечера ревьюера.

Тело изменения собирается из записи: находка, средство, слова задачи-исправителя как цитата, поверхности,
прошедшие целиком, и команды, уже падавшие на базовом коммите. Issues линкуются обычной ссылкой без
ключевого слова закрытия: merge закрыл бы их по слову платформы, тогда как закрытие здесь означает, что
capability-владелец посмотрел снова и не нашёл — это устанавливает и записывает следующий обслуживающий
прогон.

Пуш идёт по HTTPS с кредентиалом агента, токен попадает в git через credential helper, читающий
переменную окружения, а не через аргумент команды: аргумент виден каждому процессу машины. Настроенные
helper'ы предварительно сбрасываются, иначе связка ключей разработчика ответит вместо агента — та самая
подмена, против которой весь этот путь и сделан. Force-push отсутствует: ветка, которая не идёт
fast-forward, докладывается и остаётся как есть. Автор коммита — `ai-devsecops-agent` с адресом
`users.noreply`: платформы связывают коммиты с аккаунтами по почте, и правдоподобный адрес — это способ
попасть в чужой граф контрибуций без ведома человека.

Своё же изменение агент одобрить не может: GitHub запрещает ревью автору pull request, кем бы тот автор
ни был. Это и есть правильная форма — право на merge остаётся у людей и обязательных проверок, а роль
агента заканчивается на предложении проверенного изменения.

### 5.9 Фаза исправлений

Обслуживающий прогон после вердикта пытается исправить то, на что можно действовать: находка с
воспроизводимым свидетельством и названным средством, в фиксированном порядке (`security` раньше
`routine`), в пределах потолка открытых изменений из оверлея. Отбор и порядок считает код: выбор
моделью означал бы, что один и тот же репозиторий каждую неделю даёт разный набор ветвей.

**Одна задача на предмет, а не на находку.** Находки одного класса про один пин или один файл
объединяются в одну правку. Первый живой прогон этой фазы открыл три ветки с одинаковой правкой и
заплатил за три сессии — так недельный прогон превращается в шум, который перестают читать. Ветка
называется по классу и предмету, а не по advisory: строжайшая находка предмета меняется по мере
появления и закрытия advisory, и ветка, переехавшая при неизменном репозитории, открыла бы второй
pull request.

**Подагент правит файлы, всё остальное делает агент.** Индексация, сообщение коммита, ветка и позже
pull request — агентские: так сообщение выводится из находки, а не из того, как модель прочитала
инструкцию. Инструментов git и хостинга у роли `fixer` нет.

**Верификация читается из журнала вызовов, а не из ответа модели.** Оверлей группирует команды в
поверхности, библиотека решает, какие поверхности затронуты (включая связи, невидимые по путям), а
агент сверяет фактически выполненные команды: чтобы отдать ветку, нужна одна поверхность целиком и ни
одной упавшей команды среди выполненных. Правило «хотя бы одна команда» не выжило первого живого
прогона: две сессии выполнили самую дешёвую команду из пяти и отдали ветку, третья выполнила все пять,
нашла падение и отказалась — при одинаковой правке.

**Унаследованное падение отделяется от вызванного.** Упавшую команду агент повторяет в том же
worktree, приведённом к исходному состоянию. Если она падает и там, ветка всё равно не отдаётся —
красной ветке не верят независимо от причины, — но прогон сообщает, что проверки продукта были
красными до правок, и называет их. Иначе неделя отказов читается как «агент не умеет поднимать
зависимости».

## 6. Параллелизм

Задачи анализа независимы и запускаются одновременно с ограничением на число одновременных
сессий. Ограничение — не оптимизация, а необходимость: провайдеры лимитируют частоту, и без
ограничителя fan-out превращается в серию отказов.

Пишущие задачи изолированы: каждой свой git worktree, чтобы параллельные правки не мешали друг
другу и чтобы неудачная попытка не оставляла грязное дерево. Порядок внутри прогона фиксирован —
сначала класс `security`, затем `routine`, и классы никогда не смешиваются в одном изменении.

Гранулярность по умолчанию — одна задача на capability на всё изменение. Дробление включается только
когда подготовленный контекст превышает порог из конфигурации, и остаётся функцией от диффа:
группировка по каталогам, фиксированный порядок, одинаковое разбиение на одинаковом входе. Иначе
параллелизм становится источником мигающих результатов.

У дробления есть цена, которую нужно платить осознанно: ошибка, размазанная по двум файлам,
исчезает, если шарды не видят друг друга. Поэтому каждый шард получает полную сводку изменения и
только свои файлы для глубокого разбора, а группы стараются совпадать с модулями, а не резать их
поперёк.

### 6.1 Регулярный обслуживающий прогон

Прогон по расписанию отличается от ручного одним свойством: его никто не ждёт в этот момент.
Поэтому у него те же задачи, но другие ограничения — иначе он превращается в генератор шума, и
первое, что сделает команда, это отключит расписание.

**Ограничение объёма.** У прогона есть потолок на число открытых изменений от агента и на число
новых issue за один запуск. Конкретные значения — продуктовые, они живут в оверлее. При достижении
потолка агент не отбрасывает находки, а откладывает их: issue не создаётся, находка остаётся в
отчёте прогона, следующий запуск возьмёт её, когда очередь освободится. Приоритет при этом
фиксирован — сначала класс `security`, затем `routine`, а внутри класса по severity.

**Отсутствие дублей.** Здесь работает уже описанная идемпотентность по стабильному ключу: недельный
прогон обновляет существующие issue и изменения, а не создаёт вторые. Без этого свойства расписание
было бы неприемлемо в принципе, поэтому оно является предусловием, а не улучшением.

**Тишина при отсутствии новостей.** Если находок нет и ничего не изменилось, прогон не пишет
никуда: ни комментария «всё чисто», ни issue. Регулярное сообщение о том, что всё в порядке,
приучает игнорировать сообщения агента, и настоящее замечание тоже перестанут читать. Результат
такого прогона виден в манифесте — этого достаточно.

**Одновременность.** Два прогона, мутирующих одну ветку по умолчанию, спорят за одни ветки и issue,
поэтому одновременно идёт только один; пропустить неделю безопаснее. Обеспечивает это группа
concurrency самой платформы CI, а не блокировка внутри агента. Свой замок означал бы состояние,
которое нужно снимать при падении: отменённое задание оставляет его взятым, и расписание молчит уже
не неделю, а до того, как кто-нибудь заметит. Платформа умеет это сама и делает раньше, чем агент
успевает начать тратить.

**Отдельный бюджет.** У прогона по расписанию свои пределы — по времени, шагам и токенам — обычно
ниже ручного:
за ним никто не наблюдает, и ошибка конфигурации не должна оборачиваться неожиданным счётом. При
исчерпании бюджета прогон завершается неопределённо и говорит, что не проверил.

**Эскалация повторяющихся сбоев.** Неопределённый исход по расписанию никому не показывается —
статус проверки некому смотреть. Поэтому агент помнит серии сбоев (память прогонов ниже) и, когда
одна и та же причина класса «сбой» — чаще всего сменившая форму страница реестра или истёкший
доступ — встречается **второй** раз, открывает по ней **одну** issue для людей: ключ
`capability:failure:reason`, тот же механизм сверки, что и у находок, поэтому третий и четвёртый
прогон обновляют её, а не заводят вторую. Закрывается она так же, как всё остальное отслеживаемое:
проверка снова дошла до конца.

Второй, а не третий раз — потому что серия здесь считается строго: она живёт только до первого
прогона, в котором эта проверка завершилась. Счётчик «два» уже означает, что проверка не работала
две недели подряд, а не что два сбоя случайно вспомнились через месяц. Ждать третьей недели, чтобы
сообщить о неработающем сканере уязвимостей, дороже, чем изредка сообщить о двухнедельной икоте.
Одиночный сбой не эскалируется никогда: он остаётся в записи прогона и больше нигде.

Это единственный случай, когда прогон по расписанию нарушает правило тишины, и он же закрывает
главную опасность расписания: молча сломанный сканер, о котором никто не узнаёт месяцами.

**Память прогонов.** Ответ на «повторяется ли это» — единственное, что прогон не может вывести сам,
и единственное состояние, от которого зависит запись людям. Поэтому оно не в кэше: кэш имеет право
исчезнуть, и цена его потери — время, а не пропущенное сообщение. Состояние живёт в отдельном
git-ref (`refs/agent/state`, раздел 5.6) одним небольшим JSON-документом: ref не ветка, поэтому его
нет ни в чьей истории и к нему нельзя открыть изменение; коммиты цепляются друг за друга, поэтому
push никогда не нужен с `--force`; документ пишется только когда изменился, иначе прогон,
которому нечего сказать, оставлял бы по коммиту в неделю в чужом репозитории.

Родитель вычитывается перед записью, а не берётся из более раннего чтения: свежий checkout не знает
про ref, и коммит без родителя платформа справедливо отклонит. Конкурирующие записи не сливаются —
отклонённый push становится предупреждением, состояние остаётся прежним, и цена этого ровно одна:
повтор на следующей неделе прочитается как первый сбой. Это безопасная сторона ошибки.

**Не будить себя самим собой.** Комментарий на issue — законный способ начать прогон, и он же
самый очевидный способ получить бесконечный цикл: агент отвечает, ответ будит агента. Поэтому автор
события передаётся агенту (`--actor`) и проверяется до первой траты: комментарий машины (`[bot]`) не
будит вообще, а логин, под которым публикуется сам агент, останавливает прогон с результатом
`declined`. Сравнивается аккаунт, а не текст, потому что у вопроса «мой ли это комментарий» есть
ровно один честный ответ. Прогон при этом всё равно записывается: «агент отказался отвечать сам
себе» — это свойство, которое должно быть видно, а не отсутствие следа.

**Время публикации.** Расписание задаётся продуктом и должно приходиться на рабочее время команды.
Изменение от агента, появившееся в пятницу вечером, либо будет слито без внимания, либо провисит
до понедельника и устареет.

## 7. Бюджеты и деградация

Сколько может стоить прогон, задаёт продукт в оверлее, и задаёт внутри того блока, который описывает
сам прогон: `review.limits` и `maintenance.limits` — общий предел в токенах, время на задачу и
сколько задач идёт одновременно. Ни один блок не наследует другой: несколько повторённых строк
покупают то, что предел прогона виден там же, где назван сам прогон, а не собирается читателем из
секции про модели, секции про траты и секции про объём. Обслуживание, запущенное руками, живёт по тем
же числам, что и по расписанию: работа одна и та же, а второй набор чисел был бы просто вторым
местом, которое надо держать в согласии с первым.

Сколько прогон обслуживания вправе оставить после себя — вопрос другой природы: не «сколько это
стоит», а «насколько агент шумит», — поэтому это отдельный блок внутри той же секции,
`maintenance.queue`.

Ключи обязательны все, а «без потолка» пишется явным `null`: пропущенный ключ — это вопрос, на
который никто не ответил, и считать его разрешением тратить без ограничения значило бы сделать самой
дорогой настройкой ту, которую никто не набирал. Одно число остаётся за агентом, а не за продуктом —
`tool_calls_per_task`: он считает шаг, которого снаружи не видно, и стоит там как предохранитель от
сессии, переставшей двигаться вперёд.

Предела в деньгах нет намеренно. Он требует цены за модель, а предел, посчитанный по прайсу, который
никто не поддерживает, отказывает в работе по неверному числу. Появится учёт цен — появится и предел.

Параллельность ограничена не ради экономии, а потому что провайдеры считают запросы: неограниченный
веер превращается в серию отказов, а не в быстрый прогон. Общий предел и параллельность вводятся
вместе — четыре сессии, каждая в своём пределе, всё равно тратят вчетверо больше согласованного.

Поведение при исчерпании: задача завершается со статусом `exhausted`, прогон продолжает остальные
задачи, итог становится неопределённым, а в отчёте названо, что именно не проверено. Так же
записывается задача, которую общий предел не смог оплатить: не «пропущена», а «не проверено» — иначе
самым дешёвым способом пройти гейт станет исчерпать бюджет. Порядок результатов остаётся порядком
плана независимо от того, кто финишировал первым: отчёт не должен перетасовываться между прогонами.
Ретрай — один и только для транзиентных причин; повторять то, чего в экосистеме нет, бессмысленно.

Учёт стоимости идёт только по данным бэкенда. Если бэкенд не отдаёт детализацию, стоимость прогона
записывается как неизвестная, а не оценивается по своим счётчикам: в манифесте выдуманное число
выглядит ровно как настоящее, и через месяц на нём будет построен вывод «эта модель дешевле».
Оценка допустима лишь помеченной как оценка и никогда не суммируется с фактическими цифрами. Там,
где учёта нет, бюджет применяется по времени и числу шагов — ограничивать деньгами нечем, и делать
вид, что можно, хуже, чем признать предел.

## 8. Безопасность

Агент читает недоверенный код и текст, обладает правами в хостинге и обращается к внешним
моделям. Три группы мер.

**Инъекции.** Всё внешнее подаётся модели изолированным блоком с пометкой недоверенности:
содержимое файлов, дифф, описание изменения, комментарии, ответы реестров, вывод команд.
Инструкции внутри такого блока игнорируются, включая просьбы одобрить изменение, пропустить
проверку или расширить права. Вывод подагента — тоже недоверенный вход: он валидируется схемой и
никогда не исполняется как инструкция.

**Утечка кода.** Поддержка нескольких SDK означает, что исходный код может уходить разным внешним
сторонам, поэтому политика egress формулируется сразу, пока адаптер один: какой бэкенд допустим для
какого продукта,
редакция секретов до отправки промпта, запрет отправки файлов, помеченных в оверлее как
неотправляемые. Хостируемый прокси-роутер моделей не используется — это ещё одна сторона,
получающая код.

**Права.** Наименьшие привилегии, отдельный кредентиал для правок workflow-файлов, отказ работать
с fork-изменением с правами записи, запуск только по действиям человека, а для обслуживающего
прогона — дополнительная проверка, что автор комментария имеет право записи в репозиторий. Без
этой проверки любой, кто может комментировать issue, управляет агентом.

## 9. Наблюдаемость

Каждый прогон оставляет манифест: идентификатор, триггер, версия агента, digest библиотеки, хэш
оверлея, список задач с их исходами, использованные пары «бэкенд + модель», версии вызванных
утилит, потраченные токены и деньги, все свидетельства и все находки.

Манифест — не роскошь. Он отвечает на вопрос «почему агент так решил» без повторного прогона, и
он же делает возможной оценку моделей: без записанной стоимости и латентности утверждение «эта
модель лучше для этой задачи» непроверяемо.

## 10. Конфигурация

| Файл | Содержит |
| --- | --- |
| `agent/config/scenarios/*.yaml` | какие задачи существуют у playbook'а, при каком условии включаются, порог дробления |
| `agent/config/backends.yaml` | настройки адаптеров (например, песочница SDK) — без моделей и без ролей |
| `agent/config/limits.yaml` | предохранитель по числу шагов задачи и предел размера заметок оверлея |
| `agent/config/library.yaml` | пин библиотеки: версия и digest |
| `agent/config/ceiling.yaml` | потолок утилит и хостов, политика egress |
| `agent/config/storage.yaml` | путь кэша фактов, ref состояния |
| `agent/schemas/*.json` | схемы того, что производит модель: результат задачи |

Схемой описано только то, что приходит из модели, — там форма не гарантирована ничем, кроме
проверки. Свидетельство, находка и значения оверлея — типы в коде, который ими владеет: вторая
декларация той же формы в JSON рано или поздно расходится с первой, и тогда непонятно, какая из них
правда. Срок хранения записи прогона тоже не наш параметр: её хранит платформа своими правилами, и
дублировать их здесь значило бы им противоречить.

Конфигурация — часть агента, а не библиотеки: это параметры запуска, а не знание. Продукт
переопределяет из неё только то, что описано в оверлее библиотеки.

Конфигурация лежит **внутри пакета**, а не рядом с ним. Так она попадает в дистрибутив сама, без
исключений в правилах сборки, и установленный агент ведёт себя так же, как запущенный из
репозитория. Каталог целиком переопределяется флагом `--config-dir` — этого достаточно для отладки и
для продукта с особыми потолками.

Продуктовый оверлей — две сущности разной природы: `agent.yaml` со значениями и `NOTES.md` с прозой
для модели. Значения проверяются схемой при старте, и неизвестный ключ — ошибка запуска. Разбирать
значения из прозы агент не будет: переформулированное предложение меняло бы смысл молча, а молчаливо
изменившийся срок карантина хуже громкой ошибки разбора.

Оверлей организован по видам прогона: агент делает две вещи — ревьюит изменение и обслуживает
основную ветку, — и `review:` с `maintenance:` описывают каждую целиком: `provider/model` по ролям,
предел трат, а у обслуживания ещё и `queue` — сколько оно вправе оставить после себя. Обе секции
обязательны. Значений по умолчанию для них в агенте нет вовсе, поэтому продукт без них не
запускается — и это лучше, чем прогон на модели, которую никто не выбирал. Настройки адаптеров
(песочница SDK) остаются в агенте: продукт выбирает, за что платит, но не то, насколько плотно
изолировано то, за что он заплатил.

**Какой оверлей читает ревью.** Оверлей задаёт смысл находки в этом продукте: срок карантина,
задокументированные исключения, какие экосистемы вообще проверяются, и `NOTES.md`, который попадает в
промпт каждой задачи. Поэтому ревью читает оверлей **из merge-base**, а не из проверяемого изменения.
Иначе одного коммита хватило бы, чтобы обнулить карантин, выкинуть экосистему, чью зависимость это
изменение поднимает, или дописать в заметки указание модели, что заключить, — и прогон выполнил бы
это указание, отчитавшись «блокирующего нет». Изменение проверяется целиком, но правила, по которым
его судят, оно не пишет; отредактированный оверлей вступает в силу после слияния.

Когда обязательная версия — не та, что видна в дереве, ревью говорит об этом первой строкой, а
манифест пишет, из какого коммита оверлей прочитан. Два случая законно возвращаются к дереву, и оба
названы: оверлей вне репозитория не входит ни в одно изменение, а база без оверлея — это изменение,
которое его вводит, и предпочесть более раннюю версию нечему. Обслуживающий прогон читает дерево:
там оно и есть ветка по умолчанию.

## 11. Совместимость и версии

Агент объявляет поддерживаемый диапазон версий контракта библиотеки, библиотека — минимальную
версию агента. Библиотека забирается версионированным артефактом по тегу с проверкой digest;
расхождение digest или версий — ошибка старта.

Digest считается по содержимому знания — идентичность, индекс и тела проиндексированных документов, —
а не по каталогу. Иначе чекаут тега и распакованный артефакт давали бы разные digest при одинаковом
знании, и пин работал бы только в CI. Считает его сам агент (`agent pin --library`): вторая
реализация на стороне библиотеки со временем разошлась бы с той, которая проверяет, и тогда ни одна
сторона не смогла бы сказать, какая права.

Порядок релизов не меняется: сначала библиотека знаний, затем пин библиотеки внутри агента, затем
релиз агента, затем продуктовые репозитории.

## 12. Оценка качества

Без измерений выбор модели под задачу остаётся вкусом. Поэтому в репозитории агента живёт
eval-харнес, а эталоны — в `fixtures/` библиотеки, потому что они меняются вместе со знанием.

Прогон харнеса даёт по каждой задаче полноту и точность против эталона, латентность и стоимость.
Смена модели или заметная правка промпта роли проходит через харнес; ухудшение полноты по классу
`security` — блокирующее, рост стоимости — предмет обсуждения.

## 13. Реализация

Стек: Python и `uv`.

```text
/
├── README.md, DESIGN.ru.md, CHANGELOG.md
├── pyproject.toml, uv.lock
├── agent/
│   ├── cli.py                 # команды review / maintain / explain
│   ├── orchestrator.py        # прогон целиком
│   ├── planner.py             # детерминированный план из триггера и диффа
│   ├── intent.py              # классификатор свободных запросов
│   ├── library/               # загрузка артефакта, проверка digest, срез по INDEX
│   ├── overlay.py             # значения продукта по схеме и его заметки
│   ├── backends/              # порт, адаптер cursor, поддельный бэкенд для тестов
│   ├── tools/                 # детерминированные инструменты + MCP-сервер
│   ├── evidence/              # записи и хранилище прогона
│   ├── storage/               # кэш фактов, состояние в git-ref, запись прогона
│   ├── findings/              # ключи, дедупликация
│   ├── verdict.py             # таблица блокировок, исход прогона
│   ├── report/                # сборка тела отчёта
│   ├── scm/                   # адаптер GitHub
│   ├── budget.py, manifest.py
│   ├── config/                # сценарии, модели, потолок, хранилища
│   └── schemas/               # схемы свидетельства, находки, результата, оверлея
├── tests/, eval/, scripts/
└── .github/
```

Этапы, каждый заканчивается работающим срезом:

1. Каркас: CLI, загрузка библиотеки и оверлея, планировщик, манифест прогона. Без моделей.
2. Инструменты, хранилище свидетельств и кэш фактов; фаза добычи полностью детерминирована.
3. Адаптер Cursor SDK, роль `analyst`, задача `deps-vuln` от начала до конца, включая вердикт и
   отчёт.
4. Остальные задачи анализа, параллелизм, бюджеты, неопределённый исход.
5. Маппинг «роль → бэкенд и модель» и проверка совместимости роли с бэкендом.
6. Роль `fixer`, worktree, обслуживающий прогон с issue и fix-ветками, ограничители расписания.
7. Классификатор интента и пробуждение по комментарию человека.
8. Eval-харнес и первый замер; после него — осознанный выбор моделей.
9. Второй адаптер SDK — когда ядро уже проверено на первом.

## 14. Принятые решения

Решения, которые раньше были открытыми вопросами; подробности — в названных разделах.

- Хранилищ три, а не одно: запись прогона в артефакте CI, кэш неизменяемых фактов в кэше платформы,
  состояние в git-ref `refs/agent/state`. Писать в кэш и в состояние разрешено только прогонам на
  основной ветке (5.6).
- Тексты находок формулирует `analyst`; роль `writer` работает только там, где находки за текстом нет
  — в ответе человеку на комментарий (5.2, 5.3).
- Патч в ответ на «как это исправить» готовит `fixer`, а не `writer`: разница между ролями в том, что
  остаётся после сессии — проверяемое дерево или текст. Объяснение к патчу пишет тот же `fixer` в поле
  результата, поэтому слова и дифф не расходятся (5.2, 5.3).
- Соответствие «интент → курс» задано таблицей в коде, а при низкой уверенности курс всегда `answer`:
  цена неверно прочитанного комментария ограничена сессией, а не разрешением (5.2).
- Право автора комментария писать в репозиторий спрашивается у платформы, а не выводится из его роли
  в организации; неполученный ответ считается отказом (5.2).
- Стоимость берётся только из учёта бэкенда; при отсутствии учёта она неизвестна, а бюджет
  применяется по времени и шагам (7).
- Расхождение оценок по одной находке решается таблицей «строгая из двух», без эскалации к более
  сильной модели (5.7).
- Гранулярность — одна задача на capability; детерминированное дробление по каталогам включается
  только по превышению порога контекста (6).
- Порог эскалации повторяющегося сбоя — второй запуск с той же причиной, причём серия живёт только
  до прогона, в котором проверка завершилась: «два» уже означает две недели неработающей проверки
  (6.1).
- Порт бэкендов закладывается сразу под несколько агентских SDK, но реализуется один адаптер —
  Cursor SDK; второй появляется после того, как ядро проверено на первом (5.4).
- Конфигурация живёт внутри пакета и переопределяется целиком через `--config-dir` (10).
- Оверлей продукта — `agent.yaml` со значениями по схеме и `NOTES.md` с прозой; значения из прозы не
  извлекаются (10).
- Правка файлов — инструмент, а не способность бэкенда: роли `fixer` требуется тот же реестр
  инструментов, что и `analyst` (5.3).
- Исправления группируются по классу и предмету, ветка называется по ним же (5.9).
- Верификация считается пройденной только по целой поверхности; падение, воспроизводящееся на
  исходном состоянии, помечается как унаследованное, но ветку всё равно не отдаёт (5.9).
- Хостинг адресуется через `gh api`, а не через собственный HTTP-клиент: разрешение треда есть только
  в GraphQL, а токен, лимиты и пагинация уже решены в клиенте (5.8).
- Свой тред узнаётся по маркеру с ключом находки в теле комментария; тред без маркера считается
  человеческим и не изменяется (5.8).
- Публикация выключена по умолчанию и включается `--publish` (5.8).
- Токен для публикации берётся только из названных переменных окружения; сохранённый на машине вход
  клиента не используется, и без токена не публикуется ничего (5.8).
- Запрет на два одновременных прогона обеспечивает группа concurrency в CI, а не блокировка агента:
  свой замок пришлось бы снимать после падения, а забытый замок молчит дольше пропущенной недели
  (6.1).
- Память прогонов пишется только при изменении документа и цепляется коммитом за предыдущий, поэтому
  push никогда не форсируется, а прогон без новостей не оставляет следа (5.6, 6.1).
- Пробуждение проверяется по аккаунту автора события: комментарий бота не будит, а собственный логин
  агента останавливает прогон до первой траты (6.1).
- Playbook пробуждения определяется местом комментария (изменение или issue), а не его текстом:
  триггеры `comment-on-change` и `comment-on-issue` известны из события (4, 5.2).
